DTF STUDIO — AUTHORITATIVE RULES & CRITERIA
A. Roles: customer, designer, admin. Customer buys. Designer buys and uploads. Admin has independent secure login. Backend authorization is mandatory.
B. Bilingual: Arabic title + English title + Arabic description + English description are mandatory. Use Arabic/English tabs. Publishing is blocked if any field is missing; message identifies exact field/tab.
C. Product Type: T-Shirt; Mug; Cap; T-Shirt+Mug; T-Shirt+Cap; Mug+Cap; T-Shirt+Mug+Cap. Each selected product is validated independently.
D. Upload: designer uploads files and metadata only; no manual DPI/dimension/technical entry. Click + drag/drop on website; mobile upload.
E. Ready-to-Print Master: designer selects one master. Source files are not automatically master. Master must be readable/analyzable by the system. If selected master cannot be read/reviewed, reject it. Master is not restricted to PNG; any supported/readable/analyzable format may qualify.
F. Preview: previewable file and print master are separate. If no file can be displayed, publishing to customers is blocked and a displayable file is required. Explain Master with ?/Info: it is used by operator for final printing.
G. Internal analyzer: no external viewer is required for technical checking. Backend code/library reads supported files and obtains format, MIME/signature, byte size, pixel width/height, embedded DPI where available, color data/profile where supported, alpha/transparency, orientation, metadata, previewability. Calculate effective DPI from actual pixels versus required physical print size. Do not trust embedded DPI alone.
H. Preflight checks: DPI/effective DPI; pixel dimensions; physical dimensions; target print size; minimum/maximum printable size; alpha/transparency; aspect ratio; scaling/enlargement risk; supported format; DTF minimums; product-specific requirements.
I. Rules storage: rules are data-driven and versioned. Store product, min effective DPI, min/max physical dimensions, allowed formats/preview requirements, transparency/color constraints where applicable, scaling limits and other DTF criteria. Store validation result and rule/version used. Historical order decisions must remain reproducible.
J. Publish: requires all four bilingual fields, at least one previewable file, selected master, successful master preflight, and product eligibility. If no master: “Please select the design that will be used for final print.” If no previewable file: require a displayable file.
K. Delete: designer may delete one file, multiple files, or whole Design directly from Design List. Before deletion backend checks paid order, order item, printing/production job, protected master reference and other protected relationships. If protected, deny and explain. If unprotected, clean DB records, storage objects and references according to policy.
L. Empty Design: if Design reaches zero files/assets and has no protected relationship, automatically delete the empty Design and orphan records. No manual DB deletion.
M. Database: enforce ownership and integrity: User→Role; Designer→Designs; Design→Assets; Design→Product Types; Design→Master Asset; Master→Order Item; Order→Order Items; Order Item→Printing Job; protected asset references. Use constraints, transactions, backend authorization, orphan prevention and safe storage cleanup. Never delete assets required by paid/printing/production orders. Preserve historical references required for completed orders.
N. Website/mobile: one central backend/database serves website and mobile-responsive experience; products, designs, prices, stock, orders, settings and content synchronize. Do not claim both exist without verification.
O. Designer approval: 3 designs; system qualification; official admin review fixed at 5 days; if admin does not review within 5 days designer may continue under system-qualified capabilities but official Authorized label remains admin responsibility; rejection gives reasons and 5 days for replacement; second rejection escalates per approved workflow; notifications required.
P. Security: frontend hiding is never sufficient; authorization and deletion protection must be enforced server-side.
Q. Testing: every rule needs positive, negative, boundary, authorization, DB-integrity, deletion, bilingual, mobile and regression tests. AI-generated “completed” status is not evidence.

OPENCART-STYLE ADMIN RBAC TARGET — 2026-09-16
============================================================
R. ADMIN RBAC — OPENCART-STYLE OPERATING RULE
R1. The functional model is User → User Group → Permissions, independent of implementation language/framework.
R2. Each Admin user belongs to exactly one Admin User Group.
R3. A group has two independent permission sets per resource: Access and Modify.
R4. Access permits navigation/page/direct-URL/API-read access only.
R5. Modify permits mutating operations only and never implies Access unless explicitly configured by policy; UI must prevent nonsensical states or resolve them predictably.
R6. Main Administrator is a protected full-access system group. At least one enabled Main Administrator must always remain.
R7. Printing Operator is a protected least-privilege system group. Default: Dashboard + Orders + Production access, with only explicitly required order/production modifications/downloads.
R8. Main Administrator may create custom groups and configure Access/Modify per Admin resource.
R9. Users may be created, enabled/disabled, and reassigned to a group only by an authorized Main Administrator.
R10. Navigation visibility follows Access permission, but hiding controls is never security enforcement.
R11. Server-side authorization is mandatory on every protected page/API. Read operations require Access; write/mutating operations require Modify.
R12. Direct URL/API access, fake headers, stale cookies, disabled users, and client-side tampering must not bypass authorization.
R13. Permission/group/user changes are audit logged with actor, target, action, result, and timestamp.
R14. System groups may not be deleted. Custom group deletion must be blocked while users are assigned unless an explicit safe reassignment transaction occurs.
R15. Authorization policy must have one authoritative resolver; duplicate route layers must use current database identity/group state rather than trusting stale session role claims.
R16. Every RBAC change requires positive/negative/boundary/regression tests and CI evidence before being marked Implemented.
