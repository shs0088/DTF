## Engineering synthesis

### 1. Morphology must be physical-scale aware
OpenCV documents opening as erosion followed by dilation (removes small foreground objects), closing as dilation followed by erosion (fills small holes), and morphological gradient as dilation minus erosion. In Smart Prepress these operations must not use arbitrary pixel kernels. Kernel radius should be expressed or derived in physical units at locked final print size/DPI. This lets the same cleanup rule behave consistently when an artwork is printed at different sizes.

Proposed QA/processing fields:
- morphology_operation
- structuring_element_shape
- radius_px
- radius_mm_at_final_size
- removed_component_count
- removed_area_mm2
- filled_hole_count
- protected_thin_feature_loss

Opening can remove dust/islands but can also destroy intentional distressed dots and punctuation. Closing can repair tiny pinholes but can also seal intended counters/gaps. Therefore morphology must run with before/after topology checks and a reversible preview.

### 2. Screen calibration should measure the real production floor
Brandum exposes min/max dot, dot gain, AM/FM/diffusion screening, LPI, output DPI, choke, thin-line protection, white density, and a calibration wedge. The useful engineering principle is not its default numbers; it is the calibration workflow: print a wedge on the actual press/ink/film/garment/process and record the lightest reproducible dot, darkest non-solid patch, and measured dot gain.

Smart Prepress should store a ProductionCalibration object keyed by printer + ink set + film/media + RIP/PrintMode + white policy + curing/transfer condition, rather than hard-code vendor defaults.

### 3. Choke needs topology-aware protection
Brandum's separation of choke, thin-line protection, and white density reinforces that choke is geometry, not density. Before eroding a white mask, Smart Prepress should compute local feature thickness. Where 2×choke approaches or exceeds local feature width, the engine should flag or locally limit erosion rather than silently deleting support under text/hairlines.

### 4. Browser processing can stay off the UI thread
MDN documents ImageBitmapRenderingContext as available in workers and able to transfer ImageBitmap ownership to a canvas. Combined with the existing client-side processing direction, this supports a worker pipeline for decode/preview/halftone/mask generation so large jobs do not block the storefront UI. Use transferable image objects, explicit resource disposal, decoded-pixel guards, concurrency limits, and cancellation.
